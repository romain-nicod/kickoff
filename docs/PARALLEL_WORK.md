# Working several stories at once

**Last updated:** 2026-08-25 · **Origin:** written on
`agromalibio-v2-by-aigmented`, where the model below built 53 stories in
one afternoon. Every number in section 7 was measured there.

How more than one story gets built at the same time without two writers
overwriting each other. Written before it is needed, because the failure it
prevents is silent.

🔴 **The rule it exists to serve:** *what breaks is not Git, it is
simultaneous editing.* Two writers in the same directory read a file, keep it
in memory, and each writes over the other with no conflict and no message.
Observed on another project on 20/08/2026: two sessions wrote the same
missing methods into the same file, the suite stayed green, and the duplicate
was found three days later by accident.

---

## 1. The unit of work

**One story, one branch, one worktree, one writer.** Never two writers in one
directory.

```bash
git worktree add ../<project>-US-301 -b us-301-record-a-person
```

The branch is named after the story, as `CONTRIBUTING.md` requires. When it
is merged:

```bash
git worktree remove ../<project>-US-301
```

## 2. The problem nobody expects: a framework has hot files

<!-- The table below is Rails'. A static or Node project has its own
     short list — find it before the first parallel batch, not during
     it. The question is always the same: which files does almost every
     story write? -->

Splitting by story does **not** split the files. Seven files are written by
almost every story, and they are where parallel work goes wrong:

| File | Why every story wants it | What a conflict costs |
|---|---|---|
| `db/schema.rb` | Regenerated by every migration | 🔴 Worst of all. Two branches rewrite the version line and the table blocks. Resolved by hand, it produces a schema that matches no migration |
| `config/routes.rb` | Every feature adds routes | Textual conflict, easy but constant |
| `Gemfile` / `Gemfile.lock` | Any new gem | The lock file conflicts on almost every line |
| `db/seeds.rb` | Demo data for the new screens | Silent: both sets survive, and the seed runs twice |
| The layout and its navigation | Every section adds an entry | Textual |
| `.env.example` | Any new variable | Textual |
| `config/locales/*.yml` | Any new label | 🔴 **The one that has no good answer.** Every story needs keys, none may write the file, and golden rule 8 forbids the fallback of hard-coding. Both B2 stories worked around it, in two different ways, and both were right to. **The floor lays down the batch's keys with the migrations** — that is the fix, and it belongs to step 0 |
| `spec/rails_helper.rb`, `spec/support/**`, `spec/factories/**` | Every story needs a valid record and a `sign_in` helper | 🔴 **The one this list was missing.** Two parallel stories both filled the same empty user factory, and both wired FactoryBot into their own describe blocks. Found on the first parallel batch of this project |

**A conflict in `db/schema.rb` is not a merge problem, it is a correctness
problem.** The only safe resolution is to take `main`'s version, re-run
`bin/rails db:migrate`, and let Rails regenerate it. Editing it by hand is
how a column ends up in the file and not in the database.

## 3. The answer: a sequential floor, then a parallel storey

### Floor — one writer, no parallelism

Before any story of a batch is started, **one** writer lays down, in one pass,
for the whole batch:

0. **The translation keys of every story in the batch**, and the test
   plumbing. Both are needed by all of them and writable by none.
   Guessing the keys ahead is imperfect — a story will want one more —
   but a story adding a key to a file it may not touch is a merge
   conflict, while a story finding a key already there is a story that
   just works.
0b. **The test plumbing**: a factory that builds a valid record for every
   model the batch touches, `spec/support` loaded by `rails_helper.rb`,
   and the sign-in helper wired in. It is listed first because it is the
   one that gets forgotten — a factory left empty by a generator cannot
   build a record, and each story discovers that on its own.
1. **Every migration** of the batch, and the resulting `db/schema.rb`.
2. **Every route**, declared up front — which is already the method's rule:
   routes are written before the code.
3. **Every gem** the batch needs, and `Gemfile.lock` with them.
4. **The navigation**, complete, with every entry pointing at a route that
   exists — the controllers behind them may be stubs that render "not built".
5. **The seeds**, complete for the batch.
6. **`.env.example`** and the locale keys.

This is merged to `main` before anything else starts. It costs half a day and
it removes **every** hot file from the parallel phase.

### Storey — parallel writers, disjoint files

Each story writer then works only inside its own story:

```
app/models/<its model>.rb
app/controllers/<its controller>.rb
app/views/<its folder>/*
app/policies/<its policy>.rb
app/javascript/controllers/<its stimulus controller>.js
spec/**/<its specs>
```

Files are disjoint **by construction**, not by discipline.

🔴 **A story that needs to touch a hot file has revealed a defect in the
floor, not a merge problem.** The writer stops and says so; the floor is
amended and re-merged. It does not edit the file "just this once" — that is
the exact moment the guarantee is lost.

### The database is shared, and that is not obvious

🔴 **A worktree is a checkout of the same repository, so it carries the
same `config/database.yml`, so every parallel writer runs its suite
against the SAME test database.**

Two suites at once then fight over the same rows. The symptom is the
worst kind: failures that MOVE between runs, in examples that passed a
minute earlier, with nothing in the report pointing at the cause. The
natural reaction is to hunt a bug in code that is fine.

`config/database.yml` reads `TEST_DB_SUFFIX`, and each worktree sets its
own:

```bash
export TEST_DB_SUFFIX=_us_903
bin/rails db:test:prepare
```

Without the variable the name is unchanged, so a single checkout behaves
exactly as it always did.

⚠️ Found on batch B5, by running the suite while another writer was
running its own — not by reading anything. It had been true since the
first parallel batch, and every unexplained flake before it was probably
this.

### How wide

**Three writers at a time, not eight.** The constraint is not the machine, it
is that every merge has to be reviewed. Two heavy jobs at once is the standing
limit; a story writer is medium, so three is the working width.

## 3bis. Two things about worktrees that cost an hour each

Neither is about Git being hard. Both are about a signal that looks
right and is not.

### A branch checked out in a worktree cannot be checked out again

`git checkout us-903-…` fails with *"a branch named … already exists"*
while the worktree holds it. Obvious on its own — dangerous in a loop:

```bash
# 🔴 DO NOT. The checkout fails, `&&` is not there to stop it, and the
# rebase runs on whatever branch you were already on.
for b in branch-a branch-b; do
  git checkout "$b"
  git rebase main
  git push -f origin "$b"
done
```

The rebase then reports *"Current branch main is up to date"* — which
reads like success — and the force-push goes out. Nothing was destroyed
here, because `git push -f origin <branch>` pushes the LOCAL ref of that
name and not the current branch. That was luck, not design.

**Remove the worktree before rebasing its branch**, or run the rebase
inside the worktree. And put `&&` between the steps.

### The size of an agent's transcript is the wrong liveness signal

Watching the output file grow says nothing: it only grows at the end of
each exchange, so an agent writing eight files in one turn looks frozen
for minutes. `pgrep ruby` says nothing either — between two commands
there is no process, only a model call.

**The signal is the modification time of the files in its worktree:**

```bash
find .claude/worktrees/agent-*/app .claude/worktrees/agent-*/spec \
     -type f -newermt '-2 minutes' | head
```

Measured on 25/08: two agents looked stalled for thirteen minutes on the
transcript, and both had written a spec file within the same second.

## 4. Reconciliation

- **Merges are serialised.** One pull request enters `main` at a time. The
  next writer rebases on the new `main` before opening theirs.
- **The order is declared before anyone starts**, from the dependency between
  stories — never "whoever finishes first". A story that needs another's model
  waits, or the two are one story.
- **Every merge is a squash.** One commit per story on `main`, so the history
  reads as the list of stories it is.
- **A conflict outside the hot files is recorded**, not just resolved. It
  means two stories overlapped, and the split is what gets fixed.

## 5. Quality gates, from cheapest to most expensive

| # | Gate | Run by | On what | Blocks |
|---|---|---|---|---|
| **G0** | The story's own specs, written first | The writer | Its own branch | Opening the pull request |
| **G1** | The linter, the full test suite, the security scan, and the architecture guard specs | CI | The pull request | The merge |
| **G2** | Adversarial review — a reader that writes nothing | A second pair of eyes | The diff | The merge |
| **G3** | Batch acceptance — every criterion walked on the running application | A person | The merged batch | Calling the batch done |

**G1 includes the architecture guards.** Whenever an ADR in
`docs/decisions/` declares a boundary — a table prefix, a module that may
not reach into another, a naming convention — a spec in `spec/architecture/`
walks the code and fails when the boundary is crossed. 🔴 **A rule a machine
can hold is held by a machine**: a convention nobody enforces is a
convention that lasts until the batch nobody reviews.

**G2 is a reader, and it must not be the writer.** It checks three things,
none of which are taste:

1. Does the diff satisfy **the acceptance criteria of its issue, verbatim**?
   They are quoted into the issue from `specification.md` precisely so that a
   reviewer can match them without interpreting.
2. Does it break a **golden rule**? A blocked pull request names the rule by
   its number.
3. Does it break a **business rule** of `docs/specification.md`? The ones
   that get broken are always the ones stored differently from how they are
   displayed — a rate held as a fraction and shown as a percentage, a price
   frozen on a line rather than read from the catalogue.

**G3 is the one people skip, and it is the one that catches the real defects.**
The criteria are already written; walking them on a running application is the
only place where "the invoice screen is no slower than v1" — the PRD
counter-metric — is actually tested.

## 6. What never gets delegated

- **An open decision.** The `D-n` decisions listed in `docs/PRD.md` are
  answered by a person. A writer that meets one stops and asks; it never
  invents an answer and moves on. 🔴 Nor does it declare itself blocked and
  wait in silence — it asks, then carries on with everything that does not
  depend on the answer.
- **Anything touching a secret**, a production database, or a deployment.
- **A story whose deletion behaviour is not written down.** Deleting is the
  one behaviour a migration cannot put back, so it is specified before it is
  built — never inferred from what the framework does by default.

## 7. What this costs, honestly

Parallel work buys wall-clock and costs everything else: a floor pass before
each batch, a serialised merge queue, and a reviewer who is not the writer.
**Below three or four stories it is not worth it** — the floor pass alone
costs more than doing them one after another.

It is worth it on a batch of ported behaviour whose acceptance criteria are
already known and where the risk of invention is low. It is worth **nothing**
on the batch that builds the foundation every later story depends on — there,
the dependency graph is a straight line and parallelism has nothing to bite on.

### What it actually cost, measured

On the project this document comes from, 53 stories and 143 points went from
first commit to last merge in **4 h 09**, of which the first 59 minutes were
design documents and no code. The commit log splits it:

| Phase | Wall clock | Parallel? |
|---|---|---|
| Design documents — ADRs, PRD, schema, specification | 59 min | no |
| Skeleton, test framework, auth, the guard specs | 21 min | no |
| Four batches: floor pass, then fan-out | 2 h 23 | the fan-out only |

🔴 **The floor passes are roughly a third of the elapsed time and none of them
parallelise.** Migrations, routes, gems, navigation, seeds, translation keys
and test plumbing are precisely the files every writer needs. That ratio is
the number to plan with — not the throughput, which came from running eight
writers at once and transfers to nothing.

⚠️ **The floor was amended four times mid-batch**, and each amendment stopped
writers that had already read the old version. Finishing the floor before
opening the storey is cheaper than it looks.
