# Working several stories at once

**Origin:** written on `agromalibio-v2-by-aigmented` (25/08/2026), where 53
stories were built in one afternoon; every number in section 8 was measured
there. Realigned on 13/09/2026 with the delivery method by user story.

The method decides the cycle, and this page does not repeat it: one story,
one session, one worktree, one branch, one pull request; at most **four
stories at a time**; Romain merges by batches, and after each batch the
remaining pull requests are rebased on `main` (§ 4.1, § 6, § 9.5). What
follows is only what parallel stories cost in practice, and how not to pay
it twice.

🔴 **What breaks is not Git, it is simultaneous editing.** Two writers in the
same directory read a file, keep it in memory, and each writes over the other
with no conflict and no message. Observed on another project on 20/08/2026:
two sessions wrote the same missing methods into the same file, the suite
stayed green, and the duplicate was found three days later by accident.

---

## 1. Where a story's worktree lives

```bash
git -C code/{{REPO_NAME}} worktree add ../{{REPO_NAME}}-worktrees/us-301-record-a-person -b us-301-record-a-person
```

Never two writers in one directory. Removing the worktree once the pull
request is merged is part of branch hygiene: [`CONTRIBUTING.md`](../CONTRIBUTING.md).

## 2. A framework has hot files

<!-- The table below is Rails'. A static project has its own short list —
     find it before the first parallel batch, not during it. The question
     is always the same: which files does almost every story write? -->

Splitting by story does **not** split the files. A few files are written by
almost every story, and they are where parallel work goes wrong:

| File | Why every story wants it | What a conflict costs |
|---|---|---|
| `db/schema.rb` | Regenerated by every migration | 🔴 Worst of all. Two branches rewrite the version line and the table blocks. Resolved by hand, it produces a schema that matches no migration |
| `config/routes.rb` | Every feature adds routes | Textual conflict, easy but constant |
| `Gemfile` / `Gemfile.lock` | Any new gem | The lock file conflicts on almost every line |
| `db/seeds.rb` | Demo data for the new screens | Silent: both sets survive the merge |
| The layout and its navigation | Every section adds an entry | Textual |
| `.env.example` | Any new variable | Textual |
| `config/locales/*.yml` | Any new label | 🔴 **The one with no good answer.** Every story needs keys, and golden rule 8 forbids the fallback of hard-coding. Two stories on that project worked around it in two different ways |
| `test/test_helper.rb`, `test/fixtures/**` | Every story needs a valid record and a sign-in helper | 🔴 **The one the first list was missing.** Two parallel stories both filled the same empty record builder and both wired their own sign-in. Found on the first parallel batch |

**A conflict in `db/schema.rb` is not a merge problem, it is a correctness
problem.** The only safe resolution is to take `main`'s version, re-run
`bin/rails db:migrate`, and let Rails regenerate it. Editing it by hand is
how a column ends up in the file and not in the database.

## 3. Ordering the batch around the hot files

The method has the orchestrator order the stories of a batch by their
dependencies and the files they share. Two shapes, chosen **before** the
first session opens:

- **In sequence.** The story that writes a hot file goes first; the others
  carry `Dépend de : #N` and start once it is merged.
- **A floor, then a storey.** When every story of the batch needs the same
  hot files, the first story of the batch lays them down for all of them —
  migrations and `db/schema.rb`, routes, gems, navigation, seeds,
  `.env.example`, locale keys, test plumbing — as `[Task]` sub-issues of its
  own. The others depend on it, and then write only inside their own
  models, controllers, views, Stimulus controllers and tests: files disjoint
  **by construction**, not by discipline.

🔴 **A story that needs to touch a hot file has revealed a defect in the
ordering, not a merge problem.** The session stops and says so on its issue.
It does not edit the file "just this once": that is the exact moment the
guarantee is lost.

⚠️ The floor was amended four times mid-batch on that project, and each
amendment stopped writers that had already read the old version. Finishing
the floor before opening the storey is cheaper than it looks.

## 4. One test database per worktree

🔴 **A worktree is a checkout of the same repository, so it carries the same
`config/database.yml`, so every parallel session runs its suite against the
SAME test database.** Two suites at once then fight over the same rows. The
symptom is the worst kind: failures that MOVE between runs, in tests that
passed a minute earlier, with nothing in the report pointing at the cause.

`python3 scripts/after_rails_new.py` makes the test database name read
`TEST_DB_SUFFIX`, and each worktree sets its own:

```bash
export TEST_DB_SUFFIX=_us_301
bin/rails db:test:prepare
```

Without the variable the name is unchanged, so a single checkout behaves
exactly as before. Minitest's parallel workers append their own number to
that name, so the two compose. Each session also takes its own server port.

⚠️ Found on the fifth batch, by running the suite while another session was
running its own — not by reading anything. Every unexplained flake before it
was probably this.

## 5. Two things about worktrees that cost an hour each

### A branch checked out in a worktree cannot be checked out again

`git checkout us-301-…` fails while the worktree holds the branch. Obvious on
its own, dangerous in a loop:

```bash
# 🔴 DO NOT. The checkout fails, nothing stops the loop, and the rebase runs
# on whatever branch you were already on.
for b in us-301-a us-302-b; do
  git checkout "$b"
  git rebase main
  git push --force-with-lease origin "$b"
done
```

The rebase then reports *"Current branch main is up to date"*, which reads
like success. **Rebase a story's branch inside its own worktree**
(`git -C ../{{REPO_NAME}}-worktrees/us-301-a rebase origin/main`), and stop at
the first failure.

### The size of an agent's transcript is the wrong liveness signal

The transcript only grows at the end of each exchange, so an agent writing
eight files in one turn looks frozen for minutes; `pgrep ruby` says nothing
either. **The signal is the modification time of the files in its worktree:**

```bash
find ../{{REPO_NAME}}-worktrees/*/app ../{{REPO_NAME}}-worktrees/*/test \
     -type f -newermt '-2 minutes' | head
```

Measured on 25/08: two agents looked stalled for thirteen minutes on the
transcript, and both had written a test file within the same second.

## 6. A boundary a machine can hold is held by a machine

When an ADR in `docs/wiki/` declares a boundary — a table prefix, a module
that may not reach into another, a naming convention — a test in
`test/architecture/` walks the code and fails when the boundary is crossed.
It runs with `bin/rails test`, so in CI. A convention nobody enforces lasts
until the batch nobody reads closely.

## 7. What a story session never decides alone

- **An open decision.** It asks Romain on the issue, then carries on with
  everything that does not depend on the answer. It never invents an answer,
  and never waits in silence.
- **A deletion whose behaviour is not in the acceptance criteria.** Deleting
  is the one behaviour a migration cannot put back; it is specified before it
  is built, never inferred from the framework's default.
- **Anything touching a secret or production data.** Production is deployed
  only after Romain's merge, with the project's script (method § 6).

## 8. What it costs, measured

Parallel work buys wall-clock and costs everything else: ordering the batch,
rebasing after every merge, and review capacity. **Below three or four
stories it is not worth it**, and it is worth nothing on the batch that builds
the foundation every later story depends on: there, the dependency graph is a
straight line.

On the project this page comes from, 53 stories went from first commit to
last merge in **4 h 09**, of which the first 59 minutes were design documents
and no code:

| Phase | Wall clock | Parallel? |
|---|---|---|
| Design documents — ADRs, PRD, schema | 59 min | no |
| Skeleton, test framework, authentication, guard tests | 21 min | no |
| Four batches: floor, then fan-out | 2 h 23 | the fan-out only |

🔴 **The floor passes are roughly a third of the elapsed time, and none of
them parallelise.** That ratio is the number to plan with — not the
throughput, which came from eight writers at once, before the method capped
parallel stories at four, and transfers to nothing.
