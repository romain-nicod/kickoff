# Boilerplate — `rails-ready`

**The default, and you need a reason not to use it.** The application skeleton
is generated by **`rails-ready`**
([`romain-nicod/rails-ready`](https://github.com/romain-nicod/rails-ready)),
a template derived from **`minimal.rb`** — the one taught at Le Wagon's
bootcamp, in `lewagon/rails-templates`.

It is a **generator run at creation time**, not a skeleton frozen inside this
repository — which is why it never rots between framework releases.

Why this one rather than `minimal.rb` directly: it *is* `minimal.rb`, plus the
dozen things every project installs by hand in week two, minus four defects
that cost time on every single project. The asset pipeline, the stylesheet
architecture, the form helpers and the icon set are unchanged — nobody spends
day one relearning where the CSS lives.

---

## The command

Run it in the freshly cloned repository, **after** `bin/kickoff`:

```bash
rails new -d postgresql \
  -m https://raw.githubusercontent.com/romain-nicod/rails-ready/main/template.rb \
  --skip .
```

`--skip` matters: the clone already holds `README.md`, `.github/` and the
method documents. Without it, `rails new` stops on a conflict prompt for every
one of them. With it, what is already there wins.

Then:

```bash
bin/rails db:migrate
bin/dev
```

## Two failures paid on 31/08/2026 — PEF Blog

Both were observed, both stop you dead, and neither says why.

### The template aborts on `config/importmap.rb`

```
Thor::Error: The file config/importmap.rb does not appear to exist
```

The template appends importmap pins near its end. On the run that produced
this note, that file did not exist and everything after the abort was skipped —
`.env.example`, the `.gitignore` rules, the platform lock, the initial commit.
The cause was not established; the fix was:

```bash
bin/rails importmap:install
bin/rails app:template LOCATION=/tmp/rails-ready.rb   # re-run, it resumes
```

**Check before you move on:** `ls config/importmap.rb app/javascript/application.js`.

### `rails s` starts, then exits by itself

```
Detected Solid Queue has gone away, stopping Puma...
```

`config/puma.rb` loads `plugin :solid_queue`, and the Solid tables do not
exist until you do the single-database setup. The server therefore **exits a
few seconds after booting**, and a `curl` sent too early can even hit another
app on the same port and report a misleading 200.

The setup is described in rails-ready's `docs/CONFIGURATION.md` and is **not
optional to get a running server** — it is not just a hosting cost question.
Run `bin/rails solid_queue:install solid_cache:install solid_cable:install`
first: the `db/*_schema.rb` files it writes are what you copy into the
migrations.

**Check before you move on:** `grep "Listening on" your server log`, and read
the `<title>` the server actually returns.

## What it decides for you

Inherited from `minimal.rb`, unchanged:

| Choice | Instead of | Why it is kept |
|---|---|---|
| Sprockets + `sassc-rails` | Propshaft (the Rails 8 default) | The bootcamp stylesheets are SCSS |
| `bootstrap ~> 5.3` + `autoprefixer-rails` | Hand-written CSS | Grid and components on day one |
| `font-awesome-sass ~> 6.1` | Inline SVG | `icon(...)` straight from a view |
| `simple_form` | `form_with` and manual markup | `f.input` renders a Bootstrap field |
| `lewagon/rails-stylesheets` | Rails' default CSS | The component/token layout of rule 48 |
| Importmap, with Bootstrap and Popper pinned | jsbundling, Yarn, Node | No Node toolchain to keep alive |

🔴 **Sprockets and Propshaft do not coexist.** To go back to Propshaft you
remove the `sprockets-rails` and `sassc-rails` gems **and** restore
`propshaft` in the Gemfile. Half the change leaves an app that does not boot.

Added on top:

| Addition | What it prevents |
|---|---|
| `config.active_job.queue_adapter = :solid_queue` | Jobs running **synchronously without warning** |
| Solid Queue inside Puma in development | A second terminal, permanently open, that you forget to start |
| A `Procfile` with a `worker` process | The production counterpart of the line above |
| `mission_control-jobs` | No visibility on jobs that fail |
| `dotenv-rails`, `.env`, `.env.example` | Keys in the code |
| `hotwire-livereload` | Reloading by hand every ten seconds |
| `pry-byebug`, `pry-rails`, `httplog` | Debugging an outgoing API call blind |
| `faker` | Seed data nobody believes |

And **commented, with their setup steps** in
[`docs/CONFIGURATION.md`](https://github.com/romain-nicod/rails-ready/blob/main/docs/CONFIGURATION.md):
`devise`, `pundit`, `pg_search`, `ruby_llm`, `neighbor`, `cloudinary`.

🔴 **Nothing optional is switched on by default.** A project without accounts
must not ship Devise.

## The four defects it fixes

Each is marked `DEPARTURE` in the template, with its reason:

| # | `minimal.rb` does | What it costs |
|---|---|---|
| 1 | `remove_file ".github/workflows/ci.yml"` | Our CI is gone. You find out when the first pull request has no checks |
| 2 | Overwrites `.rubocop.yml` with its own | The rules the golden rules point at are not the rules that run |
| 3 | Appends `.env*` to `.gitignore` | Git keeps the last matching rule, so it swallows the `!.env.example` above it — and rule 28 depends on that file |
| 4 | Deletes the stylesheets **before** downloading the new ones | A dropped connection leaves the app with no CSS at all |

## 🔴 One repair script is still needed

```bash
python3 scripts/after_rails_new.py
```

`rails-ready` fixes defects 1 to 3 at the source, so what is left is specific
to this repository:

> `rails new` writes no `.gitignore` when one already exists — and in a cloned
> kickoff repository, one always does. `rails new --skip .` prints
> `skip .gitignore`, and Rails' own runtime rules never land. So `tmp/`,
> `log/` and `storage/` end up tracked. Measured once: **1779 files** in the
> template's own commit.

🔴 **The script cannot repair that one**, and never could: the template ends on
`git add .` and `git commit`, so the files are already in the project's first
commit by the time anything of ours runs. The rules therefore ship with the
stack layer —
[`stacks/rails/.gitignore.append`](https://github.com/romain-nicod/kickoff/blob/main/stacks/rails/.gitignore.append)
in the kickoff template, merged into this project's `.gitignore` by
`bin/kickoff` — and are in place **before** `rails new` runs. They are the
single source: no copy of them lives in the script.

What the script does about it is **check** that the rules are in force, by
asking git whether it would ignore `tmp/cache`, `log/development.log`,
`storage/`, `public/assets`, `.bundle` and `config/master.key`. If any of them
is not ignored, it says which and **exits non-zero** — that is the one failure
here that stops everything else.

Its remaining jobs: put `!.env.example` back last if something moved it,
untrack any runtime file that slipped through, point the generators at
Minitest, give the test database its per-worktree suffix, and name the missing
gems. It is idempotent, and `--dry-run` says what it would do. Its checks for
defects 1 to 3 report nothing to do — the expected outcome, not a failure.

The same thing is caught a second time, on every pull request, by the
`No generated or secret file is tracked` step of `.github/workflows/ci.yml`:
a `.gitignore` that loses those rules later fails at nothing otherwise.

## Not using it

Legitimate cases: an existing application, a stack that is not Rails, a
deliberate move to Propshaft or Tailwind. Then **write the reason in
`README.md` under "Structural decisions"**, in the same commit. A team that
finds an unexplained bare `rails new` reinstalls the whole thing on week two,
on a hunch.

## Who is authoritative

🔴 **`rails-ready` is authoritative for the template.** This document carries
